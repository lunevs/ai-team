# Самостоятельные продукты

Эпик 302; задачи 303–305. Контракт, host-оператор и UI реализованы; основной запуск 0.7.0 готов. По решению пользователя от 23.10.2026 оператор запускается вручную.

Новая история в режиме **Самостоятельный продукт** проходит PM → SA → одобрение
плана → финансовый аналитик/дизайнер/разработчик данных → разработчик приложений.
Далее отдельный host-оператор собирает пакет и выполняет тесты без сети и секретов.
QA и SA анализируют исходники и фактические проверки. Для каждой задачи создаются
feature/<task_number> и PR в release/<epic_number>. Слияние и независимое review
остаются человеческими действиями. Затем оператор разворачивает продукт, заказчик
принимает результат, release PR в main проходит отдельные CI/review/merge, создаётся tag.

## Контракт поставки

products/<product_key>/ содержит product.json с версией и хешами, исходники,
Dockerfile, docker-compose.yml, .env.example, install.md, фиксированные зависимости,
тесты, архитектуру и необходимые миграции. ZIP версионный, immutable; скачивание
проверяет SHA256 и размер через прежний local/S3 storage. Секретов внутри нет.
Модель не задаёт Docker RUN, монтирования, Docker socket, привилегии или pip lock.

Начальный профиль: Python 3.12 с доверенным lock, HTTP service на 8000 с /health и
/result либо job с /data/result.json. Прикладной код и тесты генерируются по истории,
а не копируют кредитное демо. Другие языки, произвольные build-команды и сторонние
BI-коннекторы не объявляются реализованными. Выдача файла/презентации/скаляра требует
реального соответствующего кода и бизнес-проверки; поле output_type само этого не делает.

## Общая продуктовая среда

Допускается один Docker-host и общие продуктовые PostgreSQL/BI. Для данных каждого
продукта нужны отдельные база/роль; служебная БД ai-team не используется. Каждый продукт
имеет отдельные настройки, версию и volume результатов, переносится своим пакетом.
Сеть ai-products не связана с сетями команды. Остановка команды не останавливает продукт.
По умолчанию внешняя сеть закрыта; загрузчик публичного источника настраивается отдельно.

Данные Банка России сейчас не загружаем; проектирование хранилища — будущая user story.

## Оператор

На Docker-host из корня репозитория: `python3 scripts/product_operator.py --once`
для одного задания или `--watch` для постоянного выполнения. Это доверенный оператор,
имеющий Docker-права пользователя хоста; в контейнер агента его не устанавливают.
PRODUCT_OPERATOR_TOKEN хранится в локальном .env, API проверяет его отдельно от
APP_API_TOKEN; worker его не получает. Оператор читает только одобренные задания,
проверяет пакет, выполняет фиксированные Docker-команды без shell и без вывода
credentials/модельных logs. Квитанции сохраняются в ignored .local/product-operator.

При первом продукте с needs_database оператор запускает отдельный Compose-проект
infra/products/docker-compose.yml в общей сети ai-products и создаёт собственные БД/роль
продукта без SUPERUSER/CREATEDB/CREATEROLE. Credentials сохраняются только в приватном
.local/product-operator/credentials/<key>.env, не передаются LLM и не входят в ZIP.
При утрате файла credentials оператор отказывается незаметно менять существующий пароль.
Развёрнутый продукт и его gateway не зависят от процесса оператора или служебных сетей.
Gateway публикует только loopback HTTP и фиксированный upstream продукта; приложение
остаётся исключительно во внутренней продуктовой сети, без внешнего сетевого маршрута.

Первые service/job установки и обновления продуктов без БД проверены реально. При
обновлении volume копируется при остановленном прежнем контейнере; прежние volume/image
сохраняются, при неуспехе старый контейнер возвращается. Автообновление существующего
продукта с БД блокируется: требуется конкретный backup/migration/rollback сценарий;
универсальный безопасный откат произвольных миграций не заявляется.

19 реальных Docker-проверок: сборка, unittest, health/result, изоляция, restart, повтор
deployment, новая версия, сохранение старого volume, чистая установка по install.md,
работа при выключенных api/worker/ui/git-broker/sandbox команды и job result.json.
Отдельно полный workflow на пустой disposable PostgreSQL: 13 проверок, реальные
OpenProject/BookStack, 8 mock-вызовов/$0, реальный build/test, запрет deployment без
независимого Git gate, retry без повторных LLM/артефактов, cancellation. Подробности:
stage6-product-check.json и stage6-workflow-check.json. Дополнительно выполнен реальный OpenRouter workflow: 13 проверок, 8 calls,
29 654 tokens, $0.010684782, фактический результат 42 и независимые QA/SA заключения.
В ходе проверки устранено дублирование контекста review после BudgetExceeded; usage и
лимиты не сбрасывались/не повышались. Техническая история отменена, временные БД/volumes
и контейнеры удалены. Отчёт stage6-openrouter-workflow-check.json. Это не выпуск
нового бизнес-продукта в main; независимые GitHub/human gates сохраняются.

Продуктовые volumes, PostgreSQL и приватный каталог оператора требуют собственных
backup по install.md. Командный scripts/backup_installation.py включает только служебную
инсталляцию ai-team и не является backup общей продуктовой инфраструктуры.
Пользовательские продукты этим этапом не создаются; данные ЦБ не загружались.


Две пустые продуктовые БД дополнительно проверены на общей PostgreSQL: нет административных
прав, собственные базы пусты, соединение с базой другого продукта отвергается.
Отчёт stage6-database-check.json; все технические данные/credentials удалены.

## Ручной запуск оператора

23.10.2026 пользователь выбрал ручной запуск. Постоянный пользовательский LaunchAgent
не устанавливается; запрос разрешения закрыт этим решением. Из корня проекта:

```sh
python3 scripts/product_operator.py --once
# Либо непрерывная обработка в текущем терминале:
python3 scripts/product_operator.py --watch
```

`--once` обрабатывает одно задание, а не весь цикл поставки. Для `--watch` терминал
нужно держать открытым; Ctrl+C останавливает оператор. Пока оператор не запущен,
CHECK_PENDING и DEPLOY_READY остаются в очереди; уже развёрнутые продукты продолжают
работать независимо от него. Скрипт scripts/install_product_operator.py сохранён
для возможного будущего изменения решения по отдельному указанию пользователя.
Автоматическая проверка ранее отклонила установку постоянного процесса без явного
разрешения; установка не выполнялась и больше не ожидается.

69 unit и 6 PostgreSQL integration tests прошли. Прежняя реальная история №219 и её
расход/Excel не изменялись; новый реестр продуктов пуст. Интерфейс проверен в браузере,
скриншот stage6-ui.png. Новая история: выбрать «Самостоятельный продукт», описать требования,
одобрить подготовленный план; далее действуют тесты, PR и явная бизнес-приёмка.


Воспроизведение проверок: scripts/run_stage6_workflow_checks.py (mock по умолчанию,
опция --backend openrouter выполняет платные вызовы в пределах бюджета),
scripts/run_stage6_checks.py (кратко останавливает и возвращает runtime команды),
scripts/run_stage6_database_checks.py (отказывается работать поверх уже существующей
продуктовой PostgreSQL), scripts/run_stage6_runtime_checks.py (после основной Docker-проверки).
Все сценарии создают только собственные временные fixtures и очищают их; task/KB audit сохраняется.
Профиль python-locked-v1 является версионной политикой: изменение доверенных build/dependency
правил для будущих продуктов должно вводить новую версию профиля с сохранением старой проверки.


## База Git и CI продуктов

GITHUB_PRODUCT_BASE_REF по умолчанию release/302: сначала нужно слить PR задач 303 →
304 → 305 в этот релиз. Broker проверяет отдельный product_runtime_contract.json v1;
публикация продукта не подменяется старой базой SQL demo. Если реализации ещё нет в
базе, продукт остаётся WAITING_GITHUB. После интеграции платформы в main можно явно
переключить продуктовую базу на main. GITHUB_BASE_REF кредитного demo сохраняется.

Для product PR и release PR дополнительно обязателен успешный job product-checks.
Он проверяет manifest/политику, собирает Dockerfile из проверенного профиля, запускает
unit-тесты без сети и HTTP/job smoke. Для needs_database smoke получает отдельную пустую
PostgreSQL с отдельной ролью, закрытую сеть и временный пароль; production БД не используется.
Всё удаляется после проверки. scripts/run_stage6_database_product_checks.py подтвердил
настоящий DB connect/SELECT 42 без проектирования хранилища. scripts/run_stage6_ci_checks.py
проверил именно CI entry point на экспортированном временном пакете.
Отчёты stage6-database-product-check.json и stage6-ci-check.json.

PR реализации: #37 → #38 → #39 в release/302. Без слияния финального продуктового
контракта в эту базу Git-публикация нового продукта будет ожидать интеграции.
При создании общей сети вручную используйте `docker network create --internal --label
ai-team.product-managed=true ai-products`; оператор не захватывает чужую сеть без метки.
