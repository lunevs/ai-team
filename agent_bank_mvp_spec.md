# Техническое задание: Bank AI Delivery Team — MVP

Версия: 1.10 • 22 октября 2026 • Язык реализации и документации: русский (идентификаторы в коде — английские)

## 1. Идея и цель

Разработать локально запускаемую, контейнеризированную мультиагентную команду для выполнения банковских IT- и аналитических задач. Человек-заказчик вводит user story. Агент Product Manager уточняет требования, составляет план и заводит задачи в трекере. Агенты System Analyst, Financial Analyst, Developer и QA последовательно или параллельно (где допустимо) анализируют данные, разрабатывают SQL/ETL/отчёты, проверяют результат и возвращают заказчику готовые артефакты и ссылки на задачи/документацию. Работа должна быть воспроизводимой, проверяемой и наблюдаемой.

Цель MVP: по user story «Создать витрину анализа кредитного портфеля по месяцам: остатки, DPD30+, DPD90+, NPL90+, процентные доходы, разбивка по продукту и региону» построить согласованную спецификацию, SQL-витрину в PostgreSQL, автоматические тесты и итоговый отчёт. Все данные синтетические.

## 2. Условия и границы

- Хост: Apple Mac M3 Pro, 18 GB unified memory; Docker Desktop либо совместимый Docker runtime.
- Основной стек: Python 3.12+, FastAPI, LangGraph, OpenRouter API, PostgreSQL, Docker Compose.
- LLM вызывается по HTTPS через OpenRouter (OpenAI-compatible API); ключ хранить только в переменных окружения/секретах, не коммитить и не выводить в логи.
- Для MVP использовать только синтетические/публичные данные. OpenRouter является внешним сервисом, поэтому банковские конфиденциальные данные передавать запрещено.
- Не требуется Kubernetes, production-развёртывание, прямое подключение к реальным банковским системам или полностью автономная разработка без согласований.
- Поддержать переключаемый LLM backend: `openrouter` сейчас, `ollama` или `vllm` позже, через общий интерфейс. Не привязывать бизнес-логику к конкретной модели.

## 3. Выбор self-hosted инструментов

### 3.1 Task tracking + Wiki: OpenProject Community Edition

Использовать self-hosted OpenProject Community Edition, развёрнутый в Docker. Рабочие пакеты (work packages) — единый реестр задач, подзадач, статусов, исполнителей (включая сервисные аккаунты агентов), зависимостей, комментариев, ссылок на результаты. Встроенная Wiki/проектная документация — для спецификаций, решений и отчётов. Интеграция через OpenProject API v3; предварительно проверить доступные endpoints, права и формат аутентификации в используемой версии. Нельзя предполагать, что Wiki API поддерживает произвольные операции без проверки: при отсутствии нужного API использовать отдельный адаптер документации или управляемую страницу/вложения и зафиксировать ограничение.

Альтернативы, если OpenProject окажется слишком тяжёлым для 18 GB RAM: Plane Community (таск-трекинг) + BookStack (wiki); либо компактный Forgejo Issues + Wiki как временный MVP. Не подменять выбранную платформу без явного решения и описания компромиссов. Проверить актуальные лицензии, лимиты и поддерживаемые функции перед установкой.

### 3.2 Observability

OpenTelemetry SDK (Python) + OpenTelemetry Collector + Grafana + Loki + Tempo; Prometheus опционально. Для MVP разрешён профиль `observability`, который включается отдельно, чтобы экономить RAM. Структурированные JSON-логи обязательны даже без Grafana. Учитывать совместимость версий и актуальный способ отправки логов в Loki (например, через OTel Collector). Не использовать устаревшие агенты логирования без необходимости.

Нужны панели: количество задач по статусам; время выполнения задач/агентов; количество LLM-вызовов; оценка стоимости и токенов; ошибки/повторы; latency; trace от user story до SQL/test/artifact. Метрики не должны содержать user story, содержимое промптов, SQL-результаты или секреты. Полные промпты по умолчанию не логировать.

## 4. Логическая архитектура

```
User -> Web UI -> FastAPI -> LangGraph Orchestrator
                              |-> OpenProject Adapter (work packages/wiki)
                              |-> PM Agent
                              |-> System Analyst Agent
                              |-> Financial Analyst Agent
                              |-> Developer Agent -> Git workspace + SQL sandbox
                              |-> Application Developer Agent -> API/UI/dashboard workspace
                              |-> Designer Agent -> visual standards/templates
                              |-> QA Agent -> pytest + data quality checks
                              |-> Report Builder -> HTML/Markdown/PDF (опционально PPTX)
                              |-> LLM Gateway -> OpenRouter (позже Ollama/vLLM)
                              |-> PostgreSQL (state + synthetic bank data)
                              `-> OpenTelemetry -> Collector -> Loki/Tempo/Grafana
```

Важно: OpenProject — источник истины для статусов задач и человекочитаемой проектной документации; PostgreSQL — техническое состояние workflow, checkpoint-ы, audit/event log и синтетические банковские таблицы. Код хранится в Git, а не в wiki. Большие машинные артефакты — в отдельном Docker volume/object storage с URL/ссылкой из OpenProject. Никаких рабочих task-файлов `.md` как основного трекера; исходный README и конфигурационные файлы репозитория допустимы.

## 5. Контейнеры и переносимость

`docker-compose.yml` с сервисами:
- `api`: FastAPI + LangGraph runtime;
- `worker`: фоновое выполнение долгих workflow (в MVP допускается общий образ с api, но отдельный процесс);
- `postgres`: отдельные базы/схемы для app state, OpenProject (если требуется) и synthetic_bank; предпочтительны отдельные роли и логические базы;
- `openproject`: официальный поддерживаемый Docker-способ установки, включая необходимые вспомогательные компоненты;
- `grafana`, `loki`, `tempo`, `otel-collector`: профиль `observability`;
- `ui`: веб-интерфейс Streamlit отдельным сервисом, профиль `ui` при необходимости;
- `sandbox`: ограниченный изолированный исполнитель SQL/тестов без доступа к Docker socket и без привилегий; допускается отдельный сервис.

Соблюдать: healthchecks, named volumes, restart policy, resource limits, pinned image versions, non-root users где возможно, внутренние сети, только необходимые опубликованные порты. На Apple Silicon проверять ARM64-совместимость образов; при отсутствии ARM64 фиксировать эмуляцию и стоимость по ресурсам. Не монтировать `/var/run/docker.sock` в контейнер агентов. Не давать sandbox доступ к OpenRouter-ключу или административным credentials. Для установки моделей/образов сеть нужна; runtime-изоляция в MVP ограничена политиками Docker и маршрутизацией, а не обещанием air-gap.

Перенос в облако: конфигурация только через env/secrets; никаких hardcoded localhost внутри контейнеров; Docker volumes абстрагированы; БД доступна по DSN; адаптеры хранилища и LLM; поддержка внешнего managed PostgreSQL, object storage (S3-compatible) и reverse proxy/TLS. Документировать перенос в AWS VPC/Yandex VPC: container registry, private subnets, managed DB, IAM/secrets, ingress, egress controls, backup/restore. Не заявлять, что `docker compose up` автоматически означает production security.

## 6. Роли агентов

Команда состоит из семи ролей. Отдельного агента Architect пока нет: его обязанности закреплены за System Analyst. Человек-заказчик утверждает существенные изменения объёма, план и итоговый результат.

1. **Product Manager / PM — продукт и координация.** Уточняет исходную user story и потребность заказчика; определяет цели, измеримые результаты и критерии приёмки, создаёт цели в OpenProject. Анализирует потребность рынка и конкурентов, когда это необходимо для продуктового решения, с источниками и явным отделением гипотез от фактов. Выстраивает приоритеты целей и эпиков, контролирует выполнение плана, зависимости, бюджет и отклонения. Разрешает продуктовые и организационные споры; технические решения принимает System Analyst. При конфликте требований или выходе за утверждённые границы PM выносит вопрос заказчику. Собирает итоговый отчёт и организует приёмку. Не дублирует техническую декомпозицию аналитика.
2. **System Analyst / системный аналитик и архитектор — устройство решения и техническое управление.** Определяет архитектуру всего проекта, границы компонентов, интерфейсы и требования безопасности; подробно документирует решения и причины выбора в KnowledgeBase. Декомпозирует цели на эпики и задачи в OpenProject, определяет зависимости, критерии готовности и назначает исполнителей с учётом приоритетов PM. Каждую задачу связывает со страницей документации. Читает разрешённые метаданные, определяет контракты данных, source-to-target mapping и SQL-спецификацию. Принимает технические решения, контролирует безопасность данных и архитектуры, рассматривает все PR, оставляет обратную связь и разрешает слияние после проверок. Детальную архитектуру хранилища готовит разработчик данных, аналитик проверяет её согласованность с общей архитектурой.
3. **Financial Analyst / финансовый аналитик — бизнес-смысл и экономика.** Документирует пользовательские истории в KnowledgeBase со ссылками на цели и задачи. Определяет метрики, формулы и допущения; готовит независимые контрольные примеры и предварительные расчёты. Проверяет экономический смысл и адекватность итоговых цифр, объясняет существенные отклонения и ограничения. Готовит Excel-отчёты и расчётные файлы, при необходимости презентации, по стандартам дизайнера. Результат включает паспорт метрик, расчёты, бизнес-заключение и пользовательскую документацию.
4. **Data Developer / разработчик данных — хранилище и расчёты.** Проектирует детальную архитектуру хранилища в рамках решений System Analyst; разрабатывает воспроизводимые подходы к синтетическим тестовым данным. Создаёт миграции, SQL/ETL, витрины, инструменты расчёта бизнес-метрик и технические тесты. Берёт назначенную задачу из OpenProject, реализует её в feature/<task_number>, создаёт PR в release/<epic_number>, исправляет замечания и обновляет документацию. SQL исполняет только через sandbox с разрешёнными правами.
5. **Application Developer / разработчик приложений — frontend и backend.** Реализует API, Streamlit UI, интеграции, пользовательские сценарии, дашборды и доступ к отчётам по контрактам аналитика и стандартам дизайнера. Берёт назначенную задачу из OpenProject, работает в feature/<task_number>, создаёт PR в release/<epic_number>, добавляет необходимые тесты и обновляет документацию. Согласованные архитектурные ограничения не меняет самостоятельно.
6. **Designer / дизайнер — визуальная система.** Определяет стили UI, дашбордов, отчётности, презентаций и изображений; документирует цвета, типографику, компоненты, правила графиков, подписей, единиц измерения и доступности. Готовит макеты/шаблоны, проверяет визуальное качество результатов. За бизнес-корректность чисел отвечает финансовый аналитик, за реализацию интерфейса — разработчик приложений. Изменения версионируемых шаблонов и других файлов проходят PR.
7. **QA / инженер качества — независимая проверка.** Планирует проверки по критериям приёмки, выполняет функциональные, интеграционные и end-to-end тесты, проверяет качество данных, расчёты, отчёты и пограничные случаи. Использует независимые ожидаемые значения, проверяет ограничения доступа и восстановление workflow после сбоев. Регистрирует дефекты в OpenProject, возвращает задачи исполнителям, проверяет исправления и формирует заключение о готовности релиза. Бизнес-подтверждение финансового аналитика и техническое ревью системного аналитика дополняют QA.

PM отвечает за «зачем, что и в каком порядке», System Analyst — за «как, на какие задачи разбить и кому назначить». QA не принимает продукт вместо заказчика. Оркестрация, контроль прав, бюджетов и переходов статусов реализуются кодом платформы.

Агенты должны возвращать структурированные результаты по Pydantic-схемам. Любая роль ограничена собственными инструментами. Агентам запрещены произвольные shell-команды на хосте, доступ к секретам и изменение production-данных. Все внешние действия через allowlisted tool adapters.

## 7. Workflow и человек в контуре

Статусы: `NEW -> ANALYSIS -> PLAN_REVIEW -> IN_PROGRESS -> QA -> ACCEPTANCE -> DONE` (+ `BLOCKED`, `FAILED`, `CANCELLED`).

- Создание user story в UI; создание проекта/главной задачи в OpenProject.
- PM уточняет недостающие требования (при невозможности однозначной реализации ставит `BLOCKED` с вопросами).
- PM фиксирует цель, критерии приёмки и приоритеты; Financial Analyst оформляет user story, System Analyst проектирует решение, создаёт эпики/задачи, связывает их с документацией и назначает исполнителей. Человек подтверждает план (`PLAN_REVIEW`).
- Аналитики выполняют задачи, пишут решения в документацию и оставляют ссылки в work packages.
- Developer создаёт SQL и тесты в изолированном workspace, QA выполняет тесты; допускается не более 2 автоматических циклов исправления, затем ручная эскалация.
- PM публикует итог: статус, ссылки на Git commit/SQL, тесты, отчёт, известные ограничения, стоимость LLM-вызовов.
- Человек принимает результат (`ACCEPTANCE -> DONE`).

LangGraph checkpoints должны переживать рестарт контейнера; повторный запуск не должен дублировать задачи (idempotency keys). Поддержать resume, retry/backoff, timeouts, budgets (max calls/tokens/cost), отмену задачи и журнал событий.

### 7.1. Сквозной процесс и документация

1. Получение user story → уточнение проблемы, цели и измеримых критериев → при необходимости анализ рынка/конкурентов.
2. Архитектура и анализ источников → эпики, задачи, зависимости, исполнители и приоритеты → одобрение плана заказчиком.
3. Контракты и подготовка данных → синтетические наборы → хранилище и витрины → инструменты расчёта метрик.
4. Дашборды, Excel-отчёты и при необходимости презентации; визуальные стандарты определяются до реализации соответствующих артефактов.
5. Независимые QA-проверки, проверка экономического смысла, архитектурное и security review → исправления → проверка собранного релиза эпика.
6. Передача заказчику результата и инструкции использования → приёмка → публикация версии, фиксация ограничений и задач дальнейшего развития.

На каждом этапе исполнитель обновляет свою часть KnowledgeBase и прикладывает ссылки/артефакты к задаче. System Analyst контролирует техническую согласованность, PM — полноту относительно цели. Завершение эпика не закрывает всю user story, если остаются другие необходимые эпики.

### 7.2. Таск-трекер, ветки и pull requests

- Иерархия: цель → эпик → задача/дефект. Использовать типы и связи OpenProject, доступные в проверенной версии. Для эпика вести отдельный релиз и ветку release/<epic_number>; для задачи — feature/<task_number>. Номера — стабильные уникальные ID work packages, например feature/123 и release/45; квадратные скобки в названия не входят.
- System Analyst создаёт задачи и назначает исполнителей; PM задаёт приоритеты и контролирует план. У задачи обязательны цель/эпик, исполнитель, критерии приёмки, зависимости и ссылка на документацию. При отсутствии входных данных или блокирующей зависимости задача не начинается.
- Ветка задачи создаётся от ветки её эпика. Одну задачу с общей веткой выполняет один ответственный; независимые параллельные изменения оформляются отдельными задачами. Каждый workspace изолирован, агентам не предоставляются произвольные команды на хосте.
- PR направляется в release/<epic_number> и содержит ссылки на задачу/документацию, описание результата, проверки и изменения схемы/миграций. Автоматические проверки запускаются для PR; System Analyst рассматривает каждый PR, QA проверяет результат по критериям. Автор не утверждает свой PR; если автор — System Analyst, требуется независимое ревью компетентной роли либо человека. Политика проверяется адаптером и возможностями Git-хостинга.
- После успешных проверок и ревью разрешается слияние в ветку эпика. Перед выпуском отдельно проверяется совокупный результат всех задач в release-ветке. Подготовка PR и положительное ревью не равны принятию результата заказчиком.
- После приёмки эпика выпуск сливается в main и получает тег epic-<epic_number>-v<version>; сохраняются ссылки на PR, commit, тесты, артефакты и release notes. Изменения общего кода между эпиками интегрируются по зависимостям с повторными проверками; параллельные релизы не должны молча перезаписывать изменения друг друга.
- Готовность задачи к выполнению: понятные требования, документация, критерии, зависимости и исполнитель. Готовность к закрытию: реализация, актуальная документация, проверки, независимое ревью и слияние в ветку эпика. Готовность эпика к выпуску: закрытые обязательные задачи, QA, бизнес-проверка, инструкция использования, миграции/план отката и приёмка заказчиком.
- Git-хостинг — GitHub (выбор пользователя). Рабочий репозиторий: https://github.com/lunevs/ai-team, remote origin: https://github.com/lunevs/ai-team.git. Репозиторий публичный; GitHub API подтвердил admin/push, GitHub Actions включены. На этапе 0 проверить доступ, remote, API PR/review, доступность branch protection для выбранного репозитория/тарифа и GitHub Actions для CI. Ограничения платформы явно документировать; локальный Git не считать реализацией PR-процесса, не создавать фиктивные PR. Токены хостинга передавать только интеграционному адаптеру с минимальными правами, не помещать в sandbox, Git или логи.

### 7.3. Границы ответственности и эскалация

Отдельные роли DevOps/SRE и Security в MVP не вводятся. Ответственность за инфраструктуру, CI, backup/restore, миграции и откат распределяется задачами System Analyst между разработчиками; архитекторские и security-решения остаются у него. QA проверяет соответствующие сценарии. Политики доступа, секреты, выполнение кода и слияния обеспечиваются инструментами и правами, а не только инструкциями LLM. Продуктовые споры решает PM, технические — System Analyst; изменение согласованных критериев, спор без однозначного решения и остаточный существенный риск выносятся заказчику.

## 8. Синтетическая банковская модель данных

Создать воспроизводимый seed (фиксированный random seed), минимум:
- `dim_customer` (синтетические идентификаторы, регион, сегмент);
- `dim_product` (вид кредитного продукта);
- `fact_loan` (loan_id, customer_id, product_id, origination_date, principal, annual_rate);
- `fact_loan_daily` (loan_id, date, outstanding_balance, dpd, accrued_interest, interest_income);
- `dim_calendar`.

Предусмотреть несколько месяцев истории, нулевые остатки, пропуски, досрочное погашение, DPD 29/30/89/90, переходы между корзинами, нулевые знаменатели. Определения метрик и правила агрегации документировать; не выдавать произвольные банковские формулы за общепринятые. Ожидаемая витрина: `dm_credit_portfolio_monthly` с месяцем, продуктом, регионом, balance, dpd30_balance, dpd90_balance, npl90_ratio, interest_income. Отдельно решить, что считается DPD30+ и DPD90+, как выбирается month-end snapshot и что делать с пустыми месяцами.

## 11. LLM Gateway

`LLMProvider` с методами `generate_structured`, `generate_text`, `tool_call` (если поддерживается), конфигурацией модели по роли, temperature, timeout, retry, token budget. Не предполагать, что все модели поддерживают одинаковый tool calling/structured output: реализовать проверку capabilities и fallback/валидацию. Подсчёт токенов и цены на основе возвращаемых usage/настроенных тарифов с пометкой оценочности. Не сохранять полный prompt/response в Loki; для отладки — явный opt-in с redaction и коротким retention.

## 12. Безопасность

- Только синтетические данные для OpenRouter.
- `.env.example` без секретов, реальные ключи в `.env` (gitignored) или Docker secrets; запрет на вывод токенов в логи.
- Разделить роли PostgreSQL: read-only metadata/analyst, writer только в sandbox schema, admin только для миграций.
- Ограничить egress из sandbox, сетевые доступы контейнеров, файловые пути, CPU/RAM/timeouts.
- SQL guard: разрешённые схемы/операции, запрет DDL/DML вне sandbox; проверка на стороне БД правами, а не только LLM-подсказкой.
- Prompt injection считать недоверенным вводом: содержимое user story, документов и БД не может изменять политику инструментов.
- Логировать audit events без секретов и содержимого клиентских данных; trace IDs для корреляции.
- Для будущих банковских внедрений: отдельный private LLM backend, RBAC/SSO, KMS/secrets, mTLS, DLP, approval gates, network isolation, data residency, audit retention и security review. Не заявлять compliance по факту наличия Docker/VPC.

### 19.8. Общие правила проверки и риски

- Проверки подбираются к каждому изменению; реальные интеграционные результаты отделяются от mock. Базовый воспроизводимый e2e использует фиксированные ответы LLM, реальный LLM проверяется отдельным smoke run.
- Для SQL-корректности нужны независимые ожидаемые значения; совпадение результата с тестами того же агента недостаточно.
- Источник статусов OpenProject и техническое состояние workflow требуют reconciliation; транзакцию между PostgreSQL и HTTP API заменить надёжными повторяемыми событиями, уникальными ключами и восстановлением внешних ID.

- Главные инфраструктурные риски: RAM/ARM64 OpenProject, ограничения API документации, изменения внешнего LLM API. Решения принимать по результатам этапа 0.
- Сроки в календарных днях пока не фиксировать: оценить после инфраструктурного spike и утверждения развилок. Каждый этап завершать демонстрацией, проверками и актуализацией документации.

Для каждой задачи предусмотрена feature/<ID> и PR в release/41; совместные проверки до слияния проводятся в локальной validation/epic-41.

Технические решения:
- FastAPI + отдельный worker, один non-root образ Python 3.12.13; полный requirements.lock фиксирует транзитивные зависимости. API, worker и UI не получают административные credentials.
- PostgreSQL: idempotency key + hash запроса, durable jobs с lease и heartbeat, advisory lock на историю, события, approvals, внешний реестр IDs, validated agent results и учёт LLM reservations/usage. Checkpoints LangGraph сохраняются в той же отдельной базе ai_team. Миграции запускает ai_team (владелец базы), процессы — ai_team_runtime без DDL.
- PM формирует цель/критерии/приоритеты/вопросы; SA формирует архитектуру и ацикличную декомпозицию, назначает роли. Опубликованная структура: главная user story → цель → эпики → задачи; каждая задача имеет ссылку на страницу документации. Остальные пять ролей пока представлены контрактами и назначениями, их исполнение относится к следующим этапам.
- Graph: PM → вопросы/BLOCKED либо SA → публикация → PLAN_REVIEW/interrupt → проверка сохранённого approval → IN_PROGRESS. После IN_PROGRESS этап 1 заканчивается, SQL не исполняется. Одобрение требует текущих revision и plan_digest и допустимого статуса в OpenProject.
- POST /stories требует Idempotency-Key и synthetic_only=true. При доступном трекере возвращает 201 с work package ID (200 для повтора); при недоступном трекере — 202 с сохранённым story_id и пока пустым внешним ID. Worker восстановит публикацию; ошибка внешнего сервиса не теряет историю. Этот уточнённый асинхронный контракт отражается в OpenAPI.
- Bearer AuthProvider: один локальный владелец, токен APP_API_TOKEN. Streamlit обращается только к API. /health и /ready не раскрывают credentials; readiness проверяет БД и heartbeat worker.
- Перед LLM-вызовом резервируются calls/tokens/estimated cost. Неопределённый ответ не освобождает резерв автоматически. Цена оценочная по настроенным тарифам; неизвестная/изменившаяся цена провайдера не позволяет обещать жёсткий денежный потолок. JSON mode конфигурируется, результат всегда проверяется Pydantic; tool calling моделью отключён, инструменты вызываются детерминированным кодом.
- Создание внешних сущностей использует стабильные marker IDs и reconciliation перед повтором. DB advisory lock сериализует одинаковую историю; разные истории могут выполняться параллельно. Неизвестный исход POST не повторяется вслепую. Транзакция HTTP+PostgreSQL не заявляется как атомарная: доступность внешнего результата после таймаута влияет на reconciliation.
- Отмена проверяется перед следующим действием; уже отправленный HTTP-запрос может завершиться после отмены. Такие внешние ID сохраняются для учёта; следующие действия не запускаются. Ручные CANCELLED/BLOCKED в OpenProject учитываются worker. Невыполненная синхронизация статуса записывается в outbox.
- Пользователь отдельно одобрил bootstrap runtime: роль БД без DDL/admin; семь неадминистративных участников только проекта ai-team с правами чтения/создания/изменения задач, токены только PM/SA; BookStack с чтением книг, созданием/изменением страниц и API, без удаления/управления пользователями. BookStack-доступ распространяется на локальный инстанс, токен 30 дней; OpenProject-токены до отзыва. Учётные записи создаёт операторский scripts/bootstrap_runtime.py, не агенты.

Заготовка backup будет храниться в исключённом из Git и Docker build context каталоге .backups (0700), ключ — отдельный .backup-key (0600). Снимок всех persistent volumes планируется при краткой остановке только сервисов ai-team для согласованности PostgreSQL, BookStack/MariaDB, приложений и Git workspace. Шифрование AES-256-CBC/PBKDF2 OpenSSL дополняется отдельным HMAC-SHA256 manifest/ciphertext (encrypt-then-MAC); до восстановления проверяются подпись и хеш. Восстановление допускается только в новые volumes с отдельным именем; рабочие volumes не перезаписываются. Ключ, локальный .env и резервные копии надо хранить отдельно от потерянного компьютера; этот этап не создаёт облачное хранилище или автоматическую внешнюю доставку backups.
